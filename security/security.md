# 权限模型汇总

## 一、为什么需要权限模型

回答两个问题：

- **功能权限**：这个用户能不能点这个按钮、调这个接口？
- **数据权限**：这个用户能看到哪几行数据？

权限模型就是把这两个判断**结构化**，避免硬编码 `if (user.isAdmin)` 散落在业务代码里。

## 二、主流模型速览

| 模型 | 全称 | 核心思想 | 一句话 |
|------|------|----------|--------|
| [RBAC](RBAC.md) | Role-Based Access Control | 用户 → 角色 → 权限 | 权限挂在角色上，人换角色就换权限 |
| [数据权限](data_scope.md) | Data Scope / Row-Level Filtering | 查询自动拼数据范围条件 | 控制能看到哪几行 |
| [ABAC](ABAC.md) | Attribute-Based Access Control | 属性 + 策略表达式求值 | 一切皆属性，策略说了算 |
| [ACL](ACL.md) | Access Control List | 资源挂"谁能做什么"清单 | 谁能动我这个东西 |
| [RLS](RLS.md) | Row Level Security | 数据库层强制行过滤 | 应用层绕不过去 |

## 三、模型对比

| 维度 | RBAC | 数据权限 | ABAC | ACL | RLS |
|------|------|----------|------|-----|-----|
| 粒度 | 功能级 | 行级 | 任意 | 资源级 | 行级 |
| 复杂度 | 低 | 中 | 高 | 低 | 中 |
| 灵活性 | 差 | 中 | 极强 | 中 | 中 |
| 实现层 | 应用 | 应用 | 应用 | 应用 | 数据库 |
| 典型场景 | 后台管理 | 多部门 SaaS | 多变策略 | 文档协作 | 多租户强隔离 |

## 四、组合使用

- **RBAC + 数据权限**：国内后台管理标配，功能走角色，数据走部门树。
- **RBAC + ACL**：功能权限走 RBAC，文档/项目这类细粒度资源叠一层 ACL（飞书、Notion 的"分享给谁"）。
- **ABAC 单飞**：策略多变（时间、IP、设备、风险等级都参与决策）才上，一般配 OPA。
- **RLS 兜底**：上面任何一套都可在数据库层再叠 RLS 做最终防线。

## 五、选型建议

| 业务形态 | 建议 |
|----------|------|
| 内部管理系统 | RBAC + 数据权限 |
| 协作型产品 | RBAC + ACL |
| 多租户 SaaS | RBAC + 数据权限 + RLS |
| 策略复杂多变 | ABAC（OPA / Casbin） |

## 六、实现要点

1. **统一收口**：校验放网关或注解 + 拦截器，禁止散在业务代码里。
2. **缓存**：权限列表登录后塞 Redis，改权限要主动失效。
3. **越权**：功能权限之外必须单独防**水平越权**（用户 A 改用户 B 的订单），通常靠数据权限兜底。
4. **审计**：权限变更、越权拒绝都要留日志。
